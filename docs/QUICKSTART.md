# XeFG 2x SDK quickstart

This quickstart runs the Python reference SDK (API version `0.3.0`) on
normalized application frames. It does not need Intel's DLL, a capture trace, a
capture dataset, or a replacement swapchain. It does need a model package,
which this repository does not ship.

## 1. Prerequisites

- Python 3.10 or newer.
- NumPy (installed with the SDK).
- ONNX Runtime for the default executor, or another `Executor`.
- A model package produced from captures, or obtained separately (section 3).

## 2. Install the SDK

From the checkout root:

```sh
python -m pip install .
python -m pip install ".[ort]"
```

The second command adds ONNX Runtime. The core package imports only NumPy. For
exporting packages, install the export extra:

```sh
python -m pip install ".[export]"
python -m pip install ".[export,ort]"   # exporter plus runtime executor
```

Check the installation:

```sh
python -m pip show xefg-sdk
python -c "import xefg_sdk; print(xefg_sdk.__version__)"
```

These are local checkout instructions, not a claim of a published PyPI release.

## 3. Get a model package

The SDK requires a package directory with a `manifest.json`, ONNX models, and
profile metadata; see [Model package](MODEL_PACKAGE.md). The package is
generated by the exporter and is not created by the examples. This repository
does not contain the model assets for any size.

Use existing compatible captures, or create them with the optional native
XefgProbe included in this checkout; see [Capture guide](CAPTURE_GUIDE.md).
Then export:

```sh
xefg-export --runs <capture-run-a>,<capture-run-b> --out <package-directory>
```

Add `--debug` only when you want the optional 42-output debug model. Add
`--frame N` to select a retained application frame; the default is frame 1. The
capture directories are needed for export only; the runtime and examples never
read them. See [Capture format](CAPTURE_FORMAT.md).

Keep the package outside the application-input directory, for example:

```text
work/model_package/
work/sequence/
```

The directory names are arbitrary. The runtime never reads capture datasets.

## 4. Create application inputs

The examples read a JSON manifest with one natural-image `.npz` per application
frame. Create and enter `work/sequence`, then run this snippet there. A minimal
pair at 640x360 with a 320x180 motion/depth grid matches the 640x360 mode-3
profile:

```python
from pathlib import Path

import numpy as np

width, height = 640, 360
motion_width, motion_height = 320, 180
Path("frames").mkdir(exist_ok=True)

for index in (0, 1):
    np.savez(
        "frames/frame_%04d.npz" % index,
        frame_id=np.int64(index),
        backbuffer_color=np.zeros((height, width, 4), dtype=np.uint8),
        hudless_color=np.zeros((height, width, 4), dtype=np.uint8),
        motion_vectors=np.zeros((motion_height, motion_width, 2), dtype=np.float16),
        depth=np.ones((motion_height, motion_width), dtype=np.float32),
        ui=np.zeros((height, width, 4), dtype=np.uint8),
    )
```

`sequence.json` (next to the `frames` directory):

```json
{
  "schema_version": 1,
  "package": "../model_package",
  "config": {
    "ui_mode": "AUTO",
    "profile_id": null
  },
  "frames": [
    { "path": "frames/frame_0000.npz", "reset_history": true },
    { "path": "frames/frame_0001.npz" }
  ]
}
```

`reset_history` is a per-frame key and defaults to `false`. A `true` value
starts a new history in `Xefg2xSession` without pairing against the previously
submitted frame. There is no top-level `constants` object in version 0.3.0
(unchanged from 0.2.0).

The arrays above are placeholders that match the expected shapes; a real run
needs actual application colour, motion, depth, and UI. See
[IO contract](IO_CONTRACT.md) for all fields, formats, and the explicit
`.npy`/raw form.

Notes:

- `AUTO` uses `HUDLESS_UITEXTURE` when both hudless colour and `ui` are present;
  otherwise it uses `NONE` when backbuffer colour is present. It never selects
  mode 4.
- Mode 4 (`BACKBUFFER_HUDLESS`) must be requested explicitly in `config`:
  `{"ui_mode": "BACKBUFFER_HUDLESS"}` or
  `Config(ui_mode=UiMode.BACKBUFFER_HUDLESS)`. It uses the previous/current
  `hudless_color` pair plus the current `backbuffer_color` (the presented
  backbuffer with UI already composed), and does not use `ui`.
- Inputs are normalized at the model boundary. Motion vectors must be complete
  `current_to_previous` pixel displacements on the MV grid, positive X right and
  positive Y down, including camera motion and already jitter compensated.
  Depth is raw fg78 non-inverted `R32_FLOAT` (smaller is nearer) and is not
  rescaled to `0..1`. UI is premultiplied.
- The core does not accept frame render time, camera matrices, jitter offsets,
  or motion-vector scales. An engine adapter resolves them before `FrameInputs`.
- A generated pair is always the fixed `0.5` fraction between the two frame IDs.

## 5. Run one pair

From the checkout root:

```sh
python -I examples/pair.py --manifest work/sequence/sequence.json --package work/model_package --output work/out --png
```

Use `--pair-index N` to select a different adjacent pair. `--limit N` truncates
the sequence before selecting the pair. The one-line commands work in `cmd.exe`
and Git Bash.

## 6. Run a sequence

```sh
python -I examples/sequence.py --manifest work/sequence/sequence.json --package work/model_package --output work/out --png
```

`sequence.py` uses `Xefg2xSession`. The first frame reports `history_ready` and
produces no generated image. Later frames produce `generated` results. A
per-frame `reset_history` resets the session before that frame.

## 7. Outputs

The examples write `xefg_<previous>_<current>.npy` for each generated frame.
The array is `uint8 (H, W, 4)` in `BGRA8_UNORM` order, exactly the
`generated_frame` image. With `--png`, they also write an RGBA PNG using the
standard library; no extra dependency is needed.

There is no debug reference output. The generated frame is the only deployment
output. The application's original swapchain is untouched.

## 8. Validation commands

Run these after installation:

```sh
python -I examples/pair.py --help
python -I examples/sequence.py --help
```

Both examples import only the standard library, NumPy, and `xefg_sdk`. They do
not add repository or capture-trace paths to `sys.path`, which is why
`python -I` works once the SDK is installed.

A full functional run also needs the model package and a matching profile:

```sh
python -I examples/pair.py --manifest work/sequence/sequence.json --package work/model_package --output work/out
```

## 9. Limitations

- No performance, frame-rate, latency, memory, or supported-NPU guarantee.
- No last-bit precision promise against Intel XeFG, OptiScaler, or a captured
  reference. Historical equality was to the project's research reconstruction,
  not the provider. Mode 4 is validated at 640×360 with a small remaining
  provider residual; no equality is claimed.
- Only `NONE` (mode 1), `HUDLESS_UITEXTURE` (mode 3), and explicit
  `BACKBUFFER_HUDLESS` (mode 4) are implemented; other public enum names parse
  but raise. `AUTO` still resolves only modes 1 and 3.
- Only the profiles shipped in the package are supported. There is no
  arbitrary-resolution or arbitrary-format promise. Mode-4 profiles exist at
  all five sizes and match the full research reconstruction exactly on both
  frames; 640×360 used independent application images and larger sizes used
  application-shaped arrays recovered from capture resources.
- There is no engine adapter in this SDK. The caller or a future adapter is
  responsible for complete motion vectors, jitter compensation, and adapting
  engine depth to the fg78 raw non-inverted model contract.
- The retained capture scene exercises only depth values `1.0` and `100.0`, so
  no full device-depth-range claim is made.
- The application is responsible for providing correctly normalized inputs and
  for presenting the generated image. The SDK does not create a swapchain or
  call Present.

See [Compatibility](COMPATIBILITY.md) for the pinned upstream semantics and
[IO contract](IO_CONTRACT.md) for the full input/output contract.
